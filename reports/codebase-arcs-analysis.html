Executive summary

Overall: HRF is an unusually capable, domain-specific game platform. Its explicit action records, continuation algebra, replay log, generic UI, and pluggable rule handlers support many complex asynchronous board games from one Scala.js application.

Arcs: The module has impressive breadth: base play, Leaders & Lore, The Blighted Reach, 24 Fate handlers, bots, canvas UI, metadata, and replay serialization. Its principal weakness is confidence, not apparent feature coverage: there are no application tests or CI checks, while highly mutable state and hundreds of action handlers make regressions difficult to detect.

Codebase in general

1. Browser game platform

The main Scala.js project compiles shared infrastructure and eleven game directories into one browser application. HRF registers each game’s metadata and UI; SBT adds game folders as unmanaged sources.

2. Supporting server

good-game/ is a compact Akka HTTP, Slick, and HSQLDB service. It serves the app and stores users, journals, permissions, play links, and append-only entries. It is transport/persistence, not the rules engine.

3. Local DOM fork

scala-js-dom-reduced/ is a 32,446-line local snapshot published as 2.8.0-SNAPSHOT. The main project depends on that local artifact, creating a deliberate but undocumented build prerequisite.

What is strong

  • Explicit behavior: player choices, forced steps, dice, shuffles, and randomness are modeled as serializable actions.
  • Replay-first design: actions are recorded, validated, rerunnable, and usable for undo/timelines.
  • Shared abstractions: games reuse metadata, option validation, bots, rendering primitives, hosting, logs, and serialization.
  • Domain invariants: identity trackers reject duplicate registration, unknown locations, and invalid moves.
  • Broad product scope: offline/online play, spectators, hidden information, bots, responsive canvases, and multiple games coexist.

What limits maintainability

  • Monolithic compilation: flat unmanaged source directories give weak module boundaries and compile all games together.
  • Private language: aliases such as $, |, /, %, and @@ make code concise but raise onboarding and review cost.
  • Suppressed diagnostics: the build suppresses non-exhaustive match, unreachable-code, and other warnings that matter in a state machine.
  • Minimal documentation: the README contains only three build commands; architecture, replay contracts, and release checks are implicit.
  • No automated gate: no test source tree or GitHub Actions workflow exists.

Arcs deep dive

Arcs is the second-largest game area after Root and accounts for 23.7% of application Scala lines. It is effectively a product inside the platform, with two metadata entry points: base arcs and campaign arcs-br.

Domain state

Game owns mutable setup, factions, colors, acts/chapters, ambitions, laws, boards, and four identity trackers for resources, court cards, figures, and action cards.

Rule composition

Ten core handlers cover common flow, base rules, battle, movement, guilds, Leaders & Lore, campaign, summit, and shared Fate behavior. Twenty-four Fate handlers are inserted dynamically as players acquire Fates.

Presentation + AI

A 2,116-line canvas-heavy UI renders map, court, ambitions, figures, overlays, and choices. The default “Easy” bot assigns hand-written heuristic scores; an end-of-chapter bot can clone and simulate games.

Coverage visible in source

  • Base game for three or four players with five setup cards.
  • Leaders & Lore, including multiple-lore variants.
  • Blighted Reach acts, empire/free/blight colors, summits, edicts, laws, crises, and intermissions.
  • All 24 named Fates across three acts, each with an associated FateExpansion.
  • Replay serialization, online host simulation, and multiple bot strategies.

Completeness caveat

Source breadth is not proof of rules fidelity. One campaign path still logs TODO PERFORM CRISES ON in game-blight.scala, summit validation contains TODOs, and no automated scenarios verify setup, scoring, Fate progression, or replay compatibility.

The safest conclusion is “extensive implementation with unmeasured correctness,” not “complete.”

Key findings

01

No executable safety net High

There are no application test files and no CI workflows. SBT host simulations exercise full games and serializer round trips, but they are manual executables without assertions, stable seeds, or pull-request gating. This is the dominant risk because every other issue becomes harder to change safely.

02

Manual state cloning can silently drift High

Game.cloned copies dozens of mutable fields one by one, then clones color states and trackers. Adding a field without updating the clone produces plausible but incorrect bot simulations. The risk directly affects BotEOC, which makes decisions from cloned games.

03

First-match action routing is order-sensitive High

Every action is offered to an ordered list of expansions. Dynamic Fate handlers are prepended, and the first non-unknown result wins. Overlapping handlers are not detected, so a new case may shadow another rule based on configuration and acquisition order.

04

Replay format is coupled to class shape High

The serializer reflects case classes using package prefix, class name, and parameter count. Renames, moves, parameter additions, and constructor changes can invalidate old journals. Start actions carry versions, but there is no explicit schema or migration registry. String output also lacks an escaping protocol for quotes and backslashes.

05

Large hotspots concentrate change risk Medium

game-common.scala (2,696 lines), game-blight.scala (2,425), ui.scala (2,116), and game.scala (1,873) contain much of the state transition surface. Feature locality exists, but core and campaign files remain expensive to review.

06

Compiler feedback is muted Medium

The build suppresses warnings for non-exhaustive matches and unreachable code. That is hazardous in an algebraic state machine. A small example appears in faction validation: the “minimum two factions” condition is unreachable after the earlier “minimum three” condition.

07

Build and ownership boundaries are implicit Medium

The main build depends on a locally published snapshot and compiles folders through unmanaged source paths. There is no CI codification, module dependency graph, or maintainer guide. The approach is simple, but only after a contributor learns repository-specific conventions.
